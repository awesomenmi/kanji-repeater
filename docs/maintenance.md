# 13. Организация Apps Script

Локальные файлы Google Apps Script находятся в каталоге `scripts/`. В `.clasp.json` задано `rootDir: "scripts"`, поэтому команды `clasp push` и `clasp pull` работают с этим каталогом. Манифест проекта — `scripts/appsscript.json`. Документация хранится отдельно в `docs/`.

Пользовательская установка из `README.md` выполняется через веб-интерфейс Google Sheets и Apps Script без `clasp`: пользователь создаёт Script-файлы с именами без расширения и копирует содержимое локальных `.js`-файлов. `clasp` используется для разработки и сопровождения связанного проекта.

Текущее распределение ответственности:

| Файл                        | Содержимое                                 |
| --------------------------- | ------------------------------------------ |
| `scripts/CreateLists.js` | Лист CONFIG и список активных учебных листов |
| `scripts/DailyReviewQueue.js` | Дневной лимит, бонус, сортировка и очередь |
| `scripts/GetItems.js` | Выбор элементов для повторения |
| `scripts/NotificationService.js` | Ежедневные уведомления |
| `scripts/SessionService.js` | Создание и ведение сессий |
| `scripts/SetupService.js` | Первичное создание служебных листов |
| `scripts/TelegramService.js` | Запросы к Telegram API |
| `scripts/TelegramRichTest.js.js` | Проверка Rich Messages |
| `scripts/Webhook.js` | `doPost`, `doGet` и обработка команд Telegram |

Все `.js`-файлы одного Apps Script проекта используют общее пространство функций.

Для первичной установки `setupProjectSheetsV1()` создаёт только отсутствующие `CONFIG`, `SESSIONS`, `SESSION_ITEMS` и `LOG`. Существующие данные она не меняет. `FUNCTION` проверяется, но не создаётся и не перезаписывается, поскольку его интервалы связаны с формулами учебной таблицы.

`import` и `export` не нужны.

Не следует создавать две функции с одинаковыми именами в разных файлах.

# 14. Script Properties

Используемые свойства:

| Свойство                  | Назначение                              |
| ------------------------- | --------------------------------------- |
| `TELEGRAM_BOT_TOKEN`      | Токен бота                              |
| `TELEGRAM_CHAT_ID`        | ID чата                                 |
| `TELEGRAM_WEBHOOK_SECRET` | Случайный секрет для проверки webhook |
| `TELEGRAM_WEBAPP_URL` | Необязательный URL другого опубликованного deployment `/exec` |
| `MAX_DAILY_KANJI`         | Постоянный дневной лимит                |
| `DAILY_LIMIT_BONUS_STATE` | Временный бонус и обработанные callback |
| `TELEGRAM_USER_PREFERENCES` | Язык интерфейса и форма русского обращения |

Токен Telegram и другие секреты не должны попадать в логи, сообщения Telegram или документацию.

# 15. Правила безопасного изменения проекта

Агент, который продолжает разработку, должен соблюдать следующие правила.

1. Перед изменением функции запрашивать её актуальную версию. Старые варианты из переписки могут быть уже заменены.
2. Не перестраивать весь проект ради локального изменения.
3. Не менять FUNCTION без запроса.
4. Не записывать Countdown из Apps Script.
5. Не изменять структуру SESSIONS, SESSION_ITEMS или LOG без необходимости и согласования.
6. Не удалять историю LOG при тестировании.
7. Не переименовывать рабочие функции без обновления всех вызывающих мест и триггеров.
8. Не запускать тестовые ответы `ok`, `half`, `fail` на реальных кандзи без предупреждения: они изменяют данные.
9. Проверять обработку дублированных callback.
10. Учитывать старые ACTIVE-сессии при изменении дневного лимита.
11. Не добавлять центрирование в Rich Messages.
12. После изменения webhook обновлять deployment.
13. При появлении ошибки сначала использовать журнал Apps Script и диагностические функции.
14. Предпочитать небольшие изменения с проверкой каждого этапа.

# 16. Известные ограничения и вопросы

## 16.1. Старые ACTIVE-сессии

Сессия действует до конца дня создания. При следующем обращении к боту старая `ACTIVE`-сессия получает статус `EXPIRED`, её необработанные элементы — `CANCELLED`. Обработанные элементы и LOG сохраняются.


## 16.2. Глобальная сортировка и отдельные сессии

Общая очередь сортируется по Score, но каждая сессия относится к конкретному листу.

Абсолютно глобальный порядок показа между листами не гарантирован.

## 16.3. Продолжение активной сессии

`getOrCreateActiveSessionV22()` поддерживает повторное использование существующей сессии.

Ежедневное уведомление и `/start` показывают отдельные кнопки продолжения всех активных сессий текущего дня.

## 16.4. Дедупликация увеличения лимита

Временное состояние хранит только последние 100 обработанных callback ID.

Повторная доставка очень старого callback после вытеснения его ID теоретически может привести к повторному начислению бонуса.

## 16.5. Состояние последнего обновления

После добавления временного бонуса подтверждён диагностический результат:

```json
{
  "baseLimit": 10,
  "bonus": 0,
  "maxDaily": 10,
  "processedToday": 8,
  "reservedCount": 2,
  "remaining": 0,
  "selectedCount": 0,
  "items": []
}
```

Это подтверждает корректное чтение основного лимита, отсутствие бонуса на момент теста и расчёт свободных мест.

Успешное нажатие кнопки увеличения лимита и автоматический сброс бонуса на следующий день в предоставленных результатах тестирования отдельно не подтверждены.

# 17. Цель дальнейшей разработки

Развивать Kanji Reader как устойчивую систему повторения с сохранением трёх ключевых принципов:

**Google Sheets — источник истины.**

**Apps Script — бизнес-логика и управление состоянием.**

**Telegram — интерфейс пользователя.**

Новые функции должны интегрироваться в существующую архитектуру без потери истории, нарушения формул и неконтролируемого повторного создания сессий.
